# AIR — подробный словарь и примеры

**Статус:** согласованный словарь архитектуры на 19.10.2026. Точные форматы YAML, semantics `permit`, неизвестных фактов и runtime hooks остаются предметом указанных в ADR проверок. Термины используются одинаково в архитектуре, ТЗ, кэше и диагностике.

## 1. AIR (Agent Instruction Runtime)

Система управления жизненным циклом инструкций: discovery разрешённых источников, проверка их формы и применимости, семантическая резолюция, кэширование результатов, доставка и восстановление контекста модели. Первая интеграция — Codex Desktop для Windows. В будущем планируется интеграция функциональности менеджмента skills.

**Базовая граница:** Policy отвечает, при каких условиях что обязательно, запрещено, разрешено или предпочтительно. Skill определяет, каким способом и в какой последовательности достичь результата.

## 2. Canonical Source

Исходный авторитетный материал инструкций: файл политики, проектные правила, профиль агента или прямое пользовательское указание. Каждый выбранный источник имеет identity, местоположение/происхождение, область применимости и fingerprint. Изменение исходника приводит к пересмотру зависимых результатов AIR.

Примеры видов источников: глобальная политика, native проектные инструкции и профиль специализированного агента. Здесь не предполагаются файлы с конкретными именами в репозитории AIR.

## 3. Global Policy (G)

Общие нормативные правила для поддерживаемых агентных контекстов. Их фактическая применимость может ограничиваться метаданными источника и условиями правил.

Пример: требование проверять утверждение о завершении работы по актуальным evidence. В иерархии GPA этот уровень ниже Project и Agent.

## 4. Project Policy (P)

Правила конкретного проекта или его поддерева. Источником может быть проектный `AGENTS.md` либо выбранная AIR project-policy. Позиция в дереве проекта определяет её scope; механизм доставки фиксируется отдельно в Delivery Plan.

Пример: для `repo/backend/**` обязательна локальная проверка после изменения backend-кода.

## 5. Agent Profile (A)

Специализированные ролевые инструкции агента, например `reviewer`, `researcher`, `implementer`. В первой интеграции с Codex они могут жить в `developer_instructions` custom agent TOML. Профиль влияет на GPA Resolution и обычно доставляется native Codex-механизмом.

Пример: reviewer оценивает код и формирует замечания. Приоритет Agent над Project установлен для пользовательской policy-иерархии; фактическую message-role семантику проверяет runtime-эксперимент.

## 6. User Instruction и Current User Prompt

**User Instruction** — явное требование пользователя к задаче или поведению. **Current User Prompt** — текущее сообщение пользователя, предоставленное исполняющему агенту host. Оно может изменить ранее действующую Session Directive. Способ и протокольную роль доставки определяет host.

Пример: «Для этой задачи не делай commit». Текущий Root получает это указание непосредственно с сообщением.

## 7. Session Directive

Пользовательское указание, действующее на протяжении следующих turns и подлежащее восстановлению после compaction или для субагента. Извлечение таких директив из естественного языка выполняет отдельный resolver с фиксацией provenance и scope.

Пример: «С этого момента запрашивай разрешение перед commit». Системе также необходимо сохранять последующие отмены и уточнения этого требования.

## 8. Session State

Устойчивое состояние одной resumable session: активные директивы, отменённые или заменённые версии, scope, sequence/generation и происхождение изменений. AIR читает его при compaction, resume и scoped subagent delivery. Session State сохраняется независимо от политики вытеснения вычислительных кэшей.

Пример: `sessions/<session-id>.json` с директивой `commit_requires_approval` и указанием turn её появления.

## 9. GPA и GPA Resolution

**GPA** = Global + Project + Agent, набор относительно стабильных источников без текущего пользовательского turn. **GPA Resolution** — вычисленный результат их проверки, применимости, дедупликации и разрешения конфликтов. Приоритеты: Agent > Project > Global.

Пример: общая рекомендация запускать тесты и правило `reviewer` заниматься только read-only проверкой. Resolver учитывает оба источника и сохраняет решение по их совместимости и приоритету.

## 10. Resolution Overlay

Внутреннее машинно читаемое представление решений GPA: какие правила эквивалентны, дополняют друг друга, конфликтуют, какие из них имеют приоритет и почему. Хранит handles, hashes, scope и provenance; используется компилятором, инспекцией человеком и повторным расчётом.

Пример: отношение `conflicts_with` между двумя Rule и выбранная директива `agent reviewer wins by authority`.

## 11. Conflict Decision

Одна сохраняемая резолюция материального конфликта между известными правилами в известном контексте. В decision входят ссылки на обе стороны, отношение, применимость, версия authority contract и выбранное разрешение.

Пример: `reviewer.forbid_modify` преобладает над `project.permit_modify` при совпадающем scoped-действии. Изменение области действия может потребовать пересчёта решения.

## 12. GPA Cache

Content-addressed хранилище полного результата GPA Resolution. Ключ учитывает версии/хэши источников, scope, Format Schema/Vocabulary, нормативный контракт и resolver. Cache hit позволяет применить проверенный результат без нового LLM-вызова.

Пример: `cache/gpa/<fingerprint>/resolution.json` и рядом человекочитаемый `effective.md`.

## 13. Resolution Decision Cache

Хранилище отдельных Conflict Decisions. Поддерживает повторное использование решения при локальном изменении GPA, если все необходимые semantic/context зависимости совпадают.

Пример: `cache/conflicts/<decision-key>.json`; ключ и правила инвалидации требуют контекстных fingerprints, чтобы новое третье правило не сделало решение устаревшим.

## 14. Format Schema

Версионированное определение допустимой структуры Vocabulary и Policy. AIR поставляет отдельные определения, например `schemas/vocabulary-v1.schema.json` и `schemas/policy-v1.schema.json`; поля authored файлов используют `format: air.vocabulary/v1` или `format: air.policy/v1` для выбора соответствующей проверки.

Format Schema задаёт названия полей, типы значений и требования к структуре. AIR затем выполняет детерминированные проверки имён и ссылок, используя загруженные vocabularies.

## 15. Vocabulary

Свободно создаваемый словарь понятий конкретного домена в фиксированном формате. Он объявляет operations, facts, параметры и допустимые значения/типы. Каждый экспортируемый символ сопровождается человекочитаемым `description`, раскрывающим значение понятия.

Пример: словарь namespace `zapret` может объявить `probe.execute`, полный символ `zapret.probe.execute`. Описание объясняет действие, а параметры описывают структуру данных, например `strategy: identifier`.

## 16. Operation, Fact, Parameter и Type

**Operation** — символический вид действия агента (`test.run`, `file.modify`), определённый подключённым Vocabulary. Словари задают допустимый синтаксис и schema параметров; конкретные имена свободно расширяются.

**Fact** — структурное свойство runtime-контекста, используемое декларативной применимостью (`agent.role`, `project.path`). Значения получают из подтверждённого или сконфигурированного источника фактов.

**Parameter** — именованный аргумент operation, например `strategy` для `zapret.probe.execute`.

**Type** — валидируемый вид значения: `integer`, `boolean`, `identifier`, `glob`, `list` и другие типы, которые допускает Format Schema/Vocabulary. Например `retries: integer` разрешает числовое сравнение, а `strategy: identifier` обозначает символическую ссылку.

**Extension Vocabulary** — отдельный versioned словарь с собственным namespace. Его содержание свободно в пределах формата AIR, что позволяет добавлять доменные понятия без изменения ядра parser-а.

## 17. Policy и Rule

**Policy** — authored нормативный документ, использующий зарегистрированные Vocabulary symbols. **Rule** — структурно выделенное утверждение внутри Policy. Правило описывает модальность, operation, её параметры, условие применимости и при необходимости уточняющий естественный язык.

Иллюстрация обсуждаемой формы:

```yaml
format: air.policy/v1
uses: [core@1]
rules:
  - key: delegation.contract
    modality: require
    operation: core.task.delegate
    parameters:
      required_fields: [input_scope, deliverable, acceptance_criteria, evidence]
    description: >
      Delegated work must include enough information for independent verification.
```

Пример проверяется только после принятия окончательной схемы `parameters` и объявления `core.task.delegate` в Vocabulary.

## 18. Modality и applies_if

**Modality** — нормативный оператор: `require` (обязательно), `forbid` (запрещено), `permit` (разрешено), `prefer` (предпочтительно). Точная семантика исключений `permit` остаётся предметом SCHEMA_GATE.

**applies_if** — декларативное условие применимости Rule к известным runtime facts. Поддерживает булевы композиции `all`, `any`, `not` и типизированные сравнения. Неизвестное значение факта должно обрабатываться по согласованному контракту.

Пример: правило для role `reviewer` с `applies_if: {fact: agent.role, eq: reviewer}`.

## 19. Rule Key, Handle и Content Hash

**Rule Key** — необязательное стабильное имя, написанное автором для внешних ссылок и ручных корректировок.

**Handle** — вычисляемая AIR техническая ссылка на правило, включающая источник и structural key/location.

**Content Hash** — fingerprint нормализованного содержания Rule, позволяющий обнаружить его изменение и инвалидировать зависимости.

Например `delegation.contract` — key, внутренний handle различает одноимённые правила разных источников, а SHA256 идентифицирует конкретную редакцию.

## 20. Policy IR / Policy Graph

Внутреннее представление загруженных Sources, Rules и их отношений. Узлы могут описывать источники и правила; рёбра — `contains`, `equivalent_to`, `conflicts_with`, `refines`, `overrides`. Оно используется для резолюции, кэширования и диагностики. Реализация может использовать обычные типизированные массивы и maps.

## 21. Semantic Resolver

Отдельная low-reasoning модель, получающая проверенные Rule handles и описания только для случаев, которые нельзя разрешить структурно. Возвращает ограниченные типизированные отношения и решения. AIR валидирует ссылки, типы результата и сохранность применимых источников.

Пример: определить, являются ли `evidence.acquire` и `evidence.reuse` конфликтующими требованиями при конкретных условиях.

## 22. Host Adapter и Codex Adapter

**Host** — среда, в которой исполняются агенты и которая предоставляет собственные инструкции, lifecycle и механизм доставки сообщений.

**Host Adapter** — часть интеграции AIR, сопоставляющая capabilities host с требованиями AIR: native sources, transport, message authority, lifecycle events, runtime facts, загрузка Shared Policy, пути и доступные доказательства доставки. Adapter не меняет нормативную семантику Policy. Если host не поддерживает capability, Adapter возвращает явный неподдерживаемый статус.

**Codex Adapter** — первая конкретная реализация Host Adapter, связанная с `AGENTS.md`, custom profiles, hooks, trust и механизмами Codex Desktop на Windows. Детали относятся к reference integration, не к общему языку AIR.

## 23. Delivery Plan

Вычисленный для определённого host, роли агента и lifecycle event план доставки конкретных источников. Указывает механизм (native host либо AIR-managed transport) и набор требуемых проверок. План можно изменить при подтверждённом изменении контрактов host.

Пример: custom agent profile — native, дополнительные global policies — AIR, проектный `AGENTS.md` — native.

## 24. Native Source

Canonical Source, который host предоставляет исполняющей модели штатными средствами. В первой интеграции примерами могут быть global/project `AGENTS.md` и custom agent `developer_instructions`, если их доставка подтверждена.

## 25. Managed Source

Canonical Source, для которого Delivery Plan назначил AIR механизмом доставки через hooks. Его нормативный приоритет определяется source kind и общей моделью authority, а доставка — Host Adapter.

## 26. Delivery Payload

Подготовленный AIR текст конкретного delivery-события host: отобранные применимые инструкции и, где требуется, Session Directives с явно ограниченной делегацией для текущего пользователя. AIR хранит provenance и hashes отдельно, поэтому модель получает готовые правила без служебной карты разрешения конфликтов.

## 27. Recovery Payload

Delivery Payload для восстановления актуальных инструкций после compaction, resume или другого подтверждённого lifecycle event. Собирается по GPA Resolution, Session State и Delivery Plan. Содержимое зависит от подтверждённого native recovery конкретного host.

## 28. Policy Trace

Ограниченная диагностика AIR: event, session/agent identity, fingerprints, cache hit/miss, attempt/receipt, transport outcome, duration и ошибки. Позволяет различать запланированную и фактически подтверждённую доставку. По умолчанию записываются служебные метаданные; содержимое пользовательских сообщений и полные тексты политик защищаются от попадания в trace.

## 29. Escalated Conflict Resolution

**Escalated Conflict** — существенный конфликт применимых инструкций, который нельзя разрешить детерминированно или валидным результатом Semantic Resolver. Для него вызывается [`instruction-conflict-resolution` skill](../skills/instruction-conflict-resolution/SKILL.md), использующий единый нормативный контракт, предоставленный host. Skill не переписывает источники и не присваивает себе новый authority. При недоступности контракта или неустранимой неопределённости блокируется только зависимое действие.

## 30. Resolver Availability / BLOCKED_RESOLUTION

**Cache HIT** устраняет повторный семантический вызов; **MISS** инициирует детерминированную проверку, затем выделенный дешёвый resolver только для отношений, не выводимых структурно. Невалидный ответ, timeout и отсутствие resolver не означают совместимость правил. **BLOCKED_RESOLUTION** фиксирует невозможность принять затронутое решение.
