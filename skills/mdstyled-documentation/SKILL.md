# Документация AIR в MdStyled

## Когда применять

При создании или изменении любой документации AIR, особенно HTML-схем, стилизации, интерактивности, адаптивности и предпросмотра в **MdStyled** (`OsamaAbuSitta/MDStyled`, VS Code). Оформление отделено от архитектурных решений: визуальная правка не изменяет ADR, нормативные контракты и экспериментальные статусы.

## Источник истины и известный механизм

- Актуальные файлы проекта: `docs/air.css` (все стили), `docs/air.js` (необязательная интерактивность), `docs/00_RENDER_TEST_RU.md` (диагностика), `docs/MDSTYLED_INTEGRATION_NOTES_RU.md` (проверенные детали реализации расширения).
- Источник API расширения: https://github.com/OsamaAbuSitta/MDStyled ; для изменения интеграции перепроверь код установленной/целевой версии, особенно `src/engine/config.ts`, `src/engine/index.ts`, `src/engine/renderer.ts`, `src/previewProvider.ts`.
- `@style` / `@script` разрешаются **относительно текущего Markdown-файла**, не корня workspace. MdStyled через `fs` читает файлы и **сам** вставляет содержимое в итоговые `<style>` и `<script>`. Не вставляй CSS/JS как fallback внутрь Markdown.
- Renderer пропускает сырой HTML через `sanitize-html`; некоторые теги/атрибуты удаляются. В проверенной версии `class`, `id`, `href` сохраняются, произвольные `data-air-*` нет, `<button>` не разрешён. Используй классы, ID, ссылки `<a>`; не предполагай, что любой DOM работает. Проверяй точные ограничения по версии.
- `mdstyled.config.json` не нужен при корректных `@style`/`@script`. Директива `@page` поддерживается трансформером MDStyled: она создаёт вложенный `<div class="mdstyled-root PAGE_CLASS">` внутри постоянного корня `.mdstyled-root`. Текущий CSS AIR обращается к постоянному корню и не требует `@page`. Не поддерживай два противоречивых способа подключения для одной страницы.

## Правила авторинга

1. **Читаемый Markdown прежде всего.** Заголовки, абзацы, таблицы, код, нормативные утверждения и якоря живут в Markdown. HTML нужен там, где композиция действительно выигрывает: pipeline, развилки, интерактивные схемы.
2. Каждый `docs/*.md` (и корневой `README.md`) подключает локальные ассеты:

   ```md
   <!-- @style: ./air.css -->
   <!-- @script: ./air.js -->
   ```
   Для корневого README пути `./docs/air.css` и `./docs/air.js`.
3. CSS только в `docs/air.css`. **Запрещены** ручные `<style>`, `style="..."` и inline CSS-fallback в `.md`; они маскируют сбой загрузки темы и создают дублирование.
4. JS только в `docs/air.js`; не требуй JS для доступа к содержанию схем. Все ветви и подписи видны без выполнения скрипта. JS может подсвечивать, сворачивать или переключать, но не создавать единственную копию важного текста.
5. Предпочитай компактные карточки и горизонтальные композиции с адаптацией к узкой панели VS Code. Избегай длинных вертикальных Mermaid-графов и обрезанных подписей; если используется Mermaid, обеспечь читабельность на ширине ~560 px.
6. Не вводи runtime-инструментарий, CDN, внешние JS-библиотеки или новые форматы без отдельного обоснования.
7. Классы и ID называй с префиксом `air-`; учитывай, что `sanitize-html` способен изменить HTML-дерево. Не полагайся на `data-*`, если sanitizer их не разрешает. Для интерактивных ветвей: классы `air-lane--...` + `air-flow-filter--...` и делегирование событий.

## Workflow изменения

1. Установи, **что именно неисправно**: файл не найден / директива не распознана / CSS не применён / sanitizer удалил атрибут / JS не запускается / схема не адаптивна. Не диагностируй всё как «проблема CSS».
2. Сверь используемую версию MDStyled с исходниками; любые утверждения о поддержке HTML/CSS/JS фиксируй ссылкой на код или результат runtime probe.
3. Измени минимальное число файлов. Не редактируй Shared Policy, незакрытые ADR и бизнес-смысл архитектуры при косметической работе.
4. Открой `docs/00_RENDER_TEST_RU.md` через **MdStyled: Open Preview**, не через `MdStyled Edit`: последний заменяет файлы `@style`/`@script` встроенным шаблоном. Проверки независимы:
   - внешний CSS: зелёная карточка с рамкой и псевдоэлементом «CSS ПОДКЛЮЧЕН»;
   - JS: `air-js-status` становится «подтверждён»;
   - JS→CSS: `air-css-status` становится «ПОДТВЕРЖДЁН»;
   - runtime MdStyled: `air-renderer-status` становится «ПОДТВЕРЖДЁН»;
   - корневые CSS-правила: `air-root-status` становится «ПОДТВЕРЖДЁН».
5. Если тест не прошёл: **Help → Toggle Developer Tools → Console**; сравни `[MdStyled] Preview loaded, CSS length:` и `[AIR] external CSS: loaded/missing`. Первая величина включает CSS встроенных расширений и не является доказательством загрузки `air.css`. В этой версии MDStyled ошибки чтения файла могут попадать в объединённый CSS как комментарий `Failed to load: ...`.
6. Запусти `python tools/verify_package.py`, `git diff --check`, проверь links, YAML frontmatter skill, корректность ссылок на CSS/JS, отсутствие inline fallback, сохранность предложенных `proposals/P01–P07`.
7. **Chromium-проверка только вспомогательная.** Не объявляй проблему решённой, пока не подтверждена на установленном MDStyled в Windows VS Code. Если нет доступа к этому runtime, укажи `NOT_VERIFIED_IN_MDSTYLED` и точный воспроизводимый probe.
8. После согласования зафиксируй в Git отдельным коммитом, затем обнови `SHA256SUMS` (с проверкой скриптом) и handoff.

## Критерии готовности

- Документ понятен как Markdown без темы и JavaScript; таблицы/схемы не теряют фактический смысл.
- Нет ручного CSS внутри `.md`, один источник внешних стилей и JS.
- Проверка пакета пройдена; нет неработающих локальных ссылок.
- Подтверждённая работа в MdStyled явно отделена от тестов стороннего браузера и от непроверенных предположений.
- Применённые изменения отражены в Git и `HANDOFF_CURRENT_RU.md`.
